# semaphore.rs 改动详解

## 1. 改动综述

补丁在 `os/src/sync/semaphore.rs` 中引入资源持有者统计结构 `holders: BTreeMap<tid, count>`，并在 `up()` / `down()` 时维护该映射，使信号量死锁检测能够判断等待边并构造等待图；同时将 `Semaphore.inner` 设为 `pub` 以便检测逻辑读取快照（与互斥锁的做法一致）。

## 2. 新增与修改

| 元素                                             | 类型     | 作用                                                                                                                                          |
| ------------------------------------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `use alloc::collections::{BTreeMap, VecDeque}`   | 引入容器 | `BTreeMap` 保存持有者，迭代有序且查找 O(log n)                                                                                                |
| `SemaphoreInner.holders: BTreeMap<usize, usize>` | 字段     | 记录每个线程当前占用的该信号量的单位数量                                                                                                      |
| 逻辑：`up()`                                     | 方法调整 | 释放资源时尝试将当前线程的持有计数减一（若存在），随后 `count += 1`；若 `count <= 0` 说明仍有等待者，则弹出一个等待线程、为其计数 `+1` 并唤醒 |
| 逻辑：`down()`                                   | 方法调整 | 成功（未阻塞）时立即增加当前线程持有计数；阻塞时不记录（等待态不视为拥有）                                                                    |

## 3. 细节行为说明

### 3.1 `down()`：

1. `count -= 1`；
2. 如果结果 `< 0`：当前线程入等待队列，阻塞调度，不修改 `holders`；
3. 否则：此时代表获取成功，`holders[tid] += 1`。

### 3.2 `up()`：

1. 如果当前调用者的 tid 存在于 `holders` 中：其计数 `-1`（处理重复持有释放）；计数归零时移除键（若调用者未曾持有则忽略该步骤）。
2. 增加可用计数 `count += 1`；
3. 若 `count <= 0` 表示仍有阻塞线程需要资源：弹出一个等待线程、标记其持有计数 `+1` 并唤醒；
4. 没有等待者或唤醒后直接返回。

### 3.3 计数含义

- `holders[tid] = k`：线程 tid 当前已成功获得 k 单位此信号量资源。
- 未将“正在等待”计入 holders，避免虚假所有权导致误判。

## 4. 死锁检测支持点

- 当一个线程尝试 `down()` 阻塞时（`count < 0`），检测逻辑会：
  - 遍历所有信号量，将每个等待队列中的线程与持有该信号量的所有线程建立有向边：`waiter -> holder`。
  - 为当前请求者与目标信号量持有者建立边：`requester -> holder`。
- 检测环：若任一 holder 可达 requester，则认为出现潜在死锁。

## 5. 设计权衡

- 使用 `BTreeMap` 而非 `HashMap`：稳定迭代顺序，调试与日志更友好；性能差异在小规模下可忽略。
- 每次 `up()` 都访问并减持有者计数，即便调用者并不在 `holders` 中（例如错误释放），逻辑安全无影响：不存在键则忽略。

## 6. 局限

- 不跟踪最大需求（Need），无法预测“安全序列”。
- 不区分不同资源单元的“顺序”，仅计数；若未来需更细粒度（例如资源标号），需要扩展成集合。

## 7. 小结

该改动为信号量死锁检测奠定数据基础：显式记录每个线程的占用数量，并在获取/释放路径中维护，确保等待图边关系可以准确构建。原有接口未变化，兼容旧代码。
