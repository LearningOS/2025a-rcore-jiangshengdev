# ch8 死锁检测与时间获取补丁总览

## 1. 目标与背景

本补丁在章节 ch8 分支上增加了两类功能：

1. 面向 `mutex_lock` / `semaphore_down` 的可选死锁检测；
2. 实现 `sys_get_time`，支持跨页安全写入用户态缓冲区。

历史上框架未对互斥锁/信号量的资源依赖进行分析，可能出现环形等待导致的永久阻塞。为兼容旧程序、控制开销，死锁检测按进程粒度启用：仅当进程调用 `sys_enable_deadlock_detect(1)` 后，后续资源获取操作才进行检测；检测到潜在死锁即拒绝，并返回 `-0xDEAD`。

## 3. 死锁检测设计概述

### 3.1 采用的模型

补丁使用“等待图 (Wait-For Graph)” + 环检测来判断死锁：

- 节点：线程 (tid)。
- 边 `A -> B`：表示线程 A 等待由线程 B 持有的资源（互斥锁或信号量）。
- 在尝试获取目标资源前，将“本次请求”加入图，随后执行环检测；若存在从目标持有者回到请求者的路径，则形成环，判定死锁。

与题目中银行家算法(Available/Allocation/Need)相比：

- 银行家算法适合多类可部分可分配资源的安全性预判；
- 当前场景仅需在“阻塞前”快速判断是否出现环形等待，等待图方法成本更低，代码量更小；
- 不维护全量 Need/Allocation 矩阵，而是直接从锁/信号量的“持有者 + 等待队列”推导边关系。

### 3.2 互斥锁检测关键点

- 在 `MutexBlocking` 内新增 `owner_tid: Option<usize>`，获取锁成功时写入当前线程 tid；解锁时若有等待者，则转移所有权给出队线程，否则置空。
- 死锁检测时：
  1. 读取目标互斥锁当前持有者 owner；若无持有者直接安全返回。
  2. 构建当前进程里所有阻塞型互斥锁的等待关系边：等待队列中的 tid 指向持有者 tid。
  3. 加入“本次请求”边 requester -> owner。
  4. 对图执行 DFS 环检测：是否 owner 可达 requester。

### 3.3 信号量检测关键点

- 引入 `holders: BTreeMap<tid, usize>` 记录每个线程当前占有的计数；`down()` 成功（未阻塞）时计数+1；`up()` 时计数-1，为 0 删除。
- 当 `down()` 需要阻塞（`count < 0`）时，线程进入队列，不更新 holders。
- 死锁检测：仅在无法立即获得资源且信号量 `available <= 0` 且确实存在资源拥有者时才可能出现死锁：
  1. 对所有信号量遍历：其等待队列中的每个 tid 与所有持有者之间建立边 waiter -> holder。
  2. 为当前请求者与目标信号量的所有持有者建立边 requester -> holder。
  3. 检测是否存在从任一 holder 回到 requester 的途径。

### 3.4 时间与复杂度

- 图构建：遍历进程内互斥锁/信号量列表，复杂度 O(L + E)，L 为锁/信号量数量，E 为等待队列规模之和。
- 环检测：DFS/BFS，复杂度 O(V + E)，V 为参与线程数量。
- 只在资源获取发生且开启检测时执行，开销可控。

### 3.5 正确性与潜在竞态

- 构建图时通过对各资源的 `exclusive_access()` 获取快照；读完后立即释放，减小锁持有时间。
- 与真实调度存在时间差，可能出现“检测中构建的等待图”与实际随后状态瞬间不一致，但不会导致错误拒绝已完成的获取动作；极少场景下可能出现误判（刚好在检测结束后资源将被释放），属于可接受的权衡。

### 3.6 错误码与行为

- 死锁检测失败（潜在环）时：`mutex.lock()` / `sem.down()` 返回 `-0xDEAD`（十六进制错误标记）。
- `sys_enable_deadlock_detect` 参数非法返回 `-1`。

## 4. `sys_get_time` 实现概述

- 获取微秒时间 `get_time_us()`，转换为 `TimeVal { sec, usec }`。
- 使用 `translated_byte_buffer` 处理用户指针跨页写入，避免页边界拆分导致的复制不完整。
- 若全部字节成功复制返回 0，否则 `-1`。

## 5. 新增/修改的关键字段与方法

| 结构/方法                                  | 说明                                                     |
| ------------------------------------------ | -------------------------------------------------------- |
| `MutexBlockingInner.owner_tid`             | 当前锁持有线程，用于等待图的边终点                       |
| `SemaphoreInner.holders`                   | 记录各线程持有的信号量计数，判断谁是资源拥有者           |
| `ProcessControlBlockInner.deadlock_detect` | 进程级开关，控制是否执行死锁检测                         |
| `TaskControlBlock::tid()`                  | 获取线程标识，用于图节点                                 |
| `Mutex::as_any()`                          | 允许对 `Arc<dyn Mutex>` 做动态类型判断以区分阻塞型互斥锁 |

## 6. 局限与后续可扩展方向

- 当前仅覆盖互斥锁与信号量，各类同步原语之间的“交叉死锁”未检测（例如互斥锁 + condvar + waittid 组合）。
- 采用等待图环检测，无法推演未来“最大需求”，因此失去银行家算法对“预防陷入不安全状态”的能力。
- `holders` 对信号量的语义是“当前仍占用的数量”，但没区分不同资源实例的顺序；若未来支持复杂的资源类型，需要更细粒度描述。
- 可扩展：
  1. 将互斥锁/信号量统一抽象为资源节点，构建资源-线程二部图。
  2. 使用增量更新方式缓存图，减少每次构建成本。
  3. 引入统计信息（检测次数、平均构建时间）实现性能自诊断。

## 7. 测试建议摘要

- 死锁场景：两个线程交叉获取两个互斥锁，检测开启后第二次请求返回 `-0xDEAD`。
- 正常场景：单线程或无环等待，行为与原先一致。
- 信号量：多个线程竞争计数为 1 的信号量，构造环形等待（A 等待 B，B 等待 A）验证拒绝。
- 时间：传入跨页的 `TimeVal*` 检查能正确写入。

## 8. 结论

补丁通过最小侵入式结构扩展（拥有者跟踪 + 持有计数 + 进程开关）实现了互斥锁和信号量的环检测，并提供可选启用机制，兼顾向下兼容与性能。`sys_get_time` 的实现完善了时间系统调用的语义和跨页安全性。

## 9. 测试用例示例与期望

本仓库 `user/src/bin` 中包含三个与死锁检测相关的用例，可用于快速回归：

1. 互斥锁递归获取（应检测到死锁）

- 文件：`ch8_deadlock_mutex1.rs`
- 核心逻辑：
  - 开启检测；创建阻塞型互斥锁；
  - 同一线程二次 `mutex_lock(mid)`；
  - 期望第二次返回 `-0xDEAD`；随后解锁并打印 OK。
- 与实现对齐点：`sys_mutex_lock` 在检测阶段若发现 `owner_tid == requester_tid`，直接返回 `-0xDEAD`，该用例可验证此分支。

2. 信号量可能构成环（应至少有一个线程检测到死锁）

- 文件：`ch8_deadlock_sem1.rs`
- 核心逻辑：
  - 开启检测；准备 barrier 信号量（用于起跑同步）与 3 类资源信号量（容量见 `RES_NUM`）；
  - 三个子线程分别先占有一部分资源，再在 barrier 打开后尝试额外请求 `REQUEST[tid-1]`；
  - 若 `semaphore_down` 返回 `-0xDEAD`，线程主动退出并统计失败数；
  - 期望：`failed > 0`。
- 与实现对齐点：
  - `sys_semaphore_down` 仅在 `available <= 0` 且存在持有者时才构建等待图；
  - 待图中添加边 `requester -> each(holder_of_target)` 并检测 `holder ->* requester`；
  - 本用例通过资源占用与 barrier 协调，使部分请求进入潜在环，触发检测拒绝。

3. 信号量无环（不应检测到死锁）

- 文件：`ch8_deadlock_sem2.rs`
- 核心逻辑：
  - 开启检测；准备 barrier 与两类资源（各容量为 2）；
  - 四个线程各自先占有 `ALLOC[id]` 指定的资源，待 barrier 打开后按 `REQUEST` 可能再请求另一类；
  - 若检测返回 `-0xDEAD`，线程会回滚自己已占资源并退出（计为失败）；
  - 期望：`failed == 0`。
- 与实现对齐点：等待图不会形成环，因此所有 `down()` 均成功，验证“非死锁路径”与开销可控。

提示：运行这些用例前需在用户态调用 `enable_deadlock_detect(true)` 以启用当前进程的检测开关；否则内核不进行检测，行为与旧版一致。
